anotherme 메신저 서버 구성 제안서

텍스트 채팅, 보이스톡, 영상통화를 안정적으로 운영하는 서버 그림

개발자가 아니어도 이해할 수 있도록 “물리 서버가 몇 대인지”, “각 서버 안에서 어떤 논리 서버가 도는지”, “메시지와 통화가 어떤 길로 흐르는지”를 그림 중심으로 정리했습니다.

4대

초기 권장 핵심 서버 수

앱 서버 2대 + PostgreSQL 1대 + Redis 1대. LiveKit/스토리지는 외부 관리형 서비스를 쓰는 기준입니다.

현재 소스 상태

텍스트 채팅은 폴링 방식, 보이스톡은 LiveKit 기반 골격 있음, 영상통화는 아직 미구현입니다.

가장 먼저 할 일

폴링을 WebSocket/SSE 실시간 이벤트로 바꾸고, 타이핑/온라인 상태를 Redis로 옮기는 것입니다.

1. 한 문장 요약

텍스트 채팅

현재는 3~5초마다 새로고침

사용자가 많아지면 데이터베이스 조회가 많이 늘어납니다. 실시간 소켓으로 바꾸면 카카오톡처럼 바로 도착합니다.

보이스톡

LiveKit 구조는 방향이 맞음

API 서버는 통화 시작/종료와 토큰만 관리하고, 실제 음성 데이터는 LiveKit 서버가 처리합니다.

영상통화

아직 기능 추가 필요

LiveKit을 그대로 확장하면 되지만, 앱에 카메라 권한, 영상 화면, video 타입 처리가 추가되어야 합니다.

2. 물리 서버와 논리 서버의 차이

물리 서버

실제로 돈을 내고 띄우는 서버

클라우드 VM, 컨테이너 인스턴스, 관리형 데이터베이스, 관리형 Redis처럼 실제 운영 자원이 여기에 해당합니다.

논리 서버

서버 안에서 맡는 역할

API 서버, 실시간 서버, 푸시 작업자, 통화 토큰 발급기처럼 “기능 역할”입니다. 초기에는 한 물리 서버 안에 여러 논리 서버를 같이 둘 수 있습니다.

물리 서버 1대 예: App Server A
→
안에 들어가는 역할 API + 실시간 연결 + 푸시 작업
→
사용자 입장 로그인, 채팅 보내기, 읽음 표시, 통화 요청을 처리해 줍니다.

3. 초기 운영 추천 구성: 핵심 4대 + 외부 서비스

사용자가 많지 않은 초기 서비스라면, 직접 운영해야 할 핵심 서버는 4대 정도가 현실적입니다. LiveKit, 파일 저장소, 인증, 푸시는 관리형 서비스를 쓰는 편이 안전합니다.

5. 메시지가 이동하는 길

비유하면, PostgreSQL은 “기록장”, Redis는 “무전기”, WebSocket은 “열려 있는 전화선”, Push는 “앱을 깨우는 초인종”입니다.

1

메시지 작성

사용자가 앱에서 메시지를 보냅니다.

2

API 서버 확인

로그인 사용자와 채팅방 권한을 확인합니다.

3

DB 저장

PostgreSQL에 메시지를 영구 저장합니다.

4

실시간 전달

Redis를 통해 다른 App Server에도 알려줍니다.

5

상대방 수신

온라인이면 즉시 표시, 오프라인이면 푸시 알림을 보냅니다.

6. 보이스톡/영상통화가 이동하는 길

1

전화 걸기

앱이 API 서버에 통화 생성을 요청합니다.

2

통화방 생성

서버가 calls 테이블에 ringing 상태를 저장합니다.

3

수신 알림

FCM/Web Push로 상대방 앱을 깨웁니다.

4

LiveKit 접속

양쪽 앱이 LiveKit에 접속합니다.

5

미디어 전송

음성/영상 데이터는 API 서버가 아니라 LiveKit이 처리합니다.

보이스톡

현재 코드에 골격 있음

LiveKit 토큰 발급, 통화 수락/거절/종료, 수신 전화 푸시까지 기본 구조가 있습니다.

영상통화

LiveKit으로 확장 가능

서버는 call kind를 voice/video로 구분하고, 앱은 카메라 권한과 영상 화면을 추가하면 됩니다.

7. 성장형 구성: DAU 1만 전후

8. LiveKit을 직접 운영한다면?

추천

LiveKit Cloud 사용

초기에는 직접 미디어 서버를 운영하지 않는 편이 좋습니다. 음성/영상 품질, NAT, TURN, 지역 라우팅, 장애 대응을 직접 처리하지 않아도 됩니다.

직접 운영 미디어 서버 수: 0대

대안

LiveKit 자체 구축

규모가 커지고 비용 최적화가 필요할 때 검토합니다. 처음부터 직접 운영하면 운영 난이도가 올라갑니다.

추가 서버: LiveKit SFU 2대 + TURN 1대 이상

2+

LiveKit SFU

음성/영상 스트림 중계. 한 대 장애에 대비해 최소 2대 권장.

1+

TURN Server

회사망, 통신사망, 방화벽 환경에서 통화 연결을 도와주는 우회 서버.

1~2

LiveKit Redis

LiveKit 여러 대를 묶을 때 필요한 상태 공유. 기존 Redis와 분리 권장.

9. 현재 코드에서 위험한 지점

위험 1

폴링이 많음

채팅방 목록 5초, 메시지 3초, 타이핑 2초, 수신전화 3초마다 서버를 계속 두드립니다. 사용자가 늘면 DB 부하가 먼저 커집니다.

위험 2

타이핑 상태가 서버 메모리

App Server가 2대 이상이면 A 서버에서 입력한 타이핑 상태를 B 서버 사용자가 못 볼 수 있습니다. Redis로 옮겨야 합니다.

주의 3

영상통화는 미구현

서버 토큰은 확장 가능하지만, 앱 화면과 카메라 publish 로직이 없습니다.

주의 4

외부 비밀키 필요

Clerk, LiveKit, Firebase, VAPID, Object Storage 환경 변수가 없으면 실제 운영 기능이 제한됩니다.

10. 단계별 실행 계획

1단계

현재 구조 안정화

DB 백업, 환경 변수, LiveKit Cloud, FCM, VAPID 설정을 완료합니다.

2단계

실시간 채팅 도입

WebSocket/SSE와 Redis Pub/Sub을 추가해 메시지/읽음/타이핑을 즉시 전달합니다.

3단계

보이스톡 품질 개선

통화 상태도 실시간 이벤트로 바꾸고, 통화 실패/끊김/재연결 로그를 수집합니다.

4단계

영상통화 확장

call kind, 카메라 권한, 영상 UI, LiveKit video track 처리를 추가합니다.
